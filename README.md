# ExtractAfricaData

### **Project Overview**
This project is a **data ingestion pipeline** for climate and development indicators across African countries.

In simple terms, it does three jobs:
1. **Extracts data** from multiple public sources (World Bank, FAO, OECD, Africa Energy Portal, and others).
2. **Cleans and standardizes** the data into one consistent format.
3. **Validates and loads** the cleaned records into PostgreSQL, while generating validation reports.

The purpose is to solve a common analytics problem: data is spread across different APIs and files, each with different column names, country names, and formats. This project creates a reliable, reusable pipeline so the data can be used for dashboards, analysis, and modeling.

---

### **Repository Structure**
Below is a practical guide to the important files and folders.

#### **Root files**
- `main.py`  
  Main command-line entry point. Lets you run one sector or all sectors in parallel.
- `config.py`  
  Loads environment variables (`.env`), defines DB settings, report path, and year ranges.
- `constants.py`  
  Canonical country list, country normalization rules, and reusable indicator lists.
- `clean_transform.py`  
  Core transformation engine that turns raw tables into standardized records.
- `validate.py`  
  Validation + PostgreSQL upsert layer. Also writes validation reports.
- `utils.py`  
  Utility helpers for type parsing, header normalization, date parsing, etc.
- `requirements.txt`  
  Python dependencies used by this project.
- `aquastat.csv`  
  Example/output CSV generated by the AQUASTAT extractor.

#### **Extractor modules (`extractors/`)**
Each file focuses on one domain and source set:
- `extractors/energy_data.py` → Energy indicators (Africa Energy Portal + World Bank WDI).
- `extractors/aquastat.py` → FAO AQUASTAT water/agriculture indicators.
- `extractors/nature_faostat.py` → FAOSTAT nature/biodiversity indicators.
- `extractors/wdi_adaptation.py` → Adaptation & resilience indicators from WDI.
- `extractors/cfcm_oecd.py` → Climate finance & carbon market data (OECD + WDI).
- `extractors/mining.py` → Green mining/manufacturing indicators from multiple sources.
- `extractors/infra_data.py` → Sustainable infrastructure and urbanization indicators.

#### **Reports (`reports/`)**
- Stores generated validation reports, for example:
  - `VALIDATION_REPORT_adaptation_*.txt`
  - `VALIDATION_REPORT_energy_*.txt`

These reports show accepted vs dropped rows and data quality issues.

### **Setup Instructions**

#### **1) Prerequisites**
- [uv](https://docs.astral.sh/uv/) installed (Python package + project manager)
- Python 3.10+ available on your system
- PostgreSQL database reachable from your machine
- Internet access (extractors call external APIs)

#### **2) Clone and enter the project**
```bash
git clone <your-repo-url>
cd ExtractAfricaData
```

#### **3) Initialize the project with uv**
If this repository does not yet have a `pyproject.toml`, initialize one:
```bash
uv init --name extractafricadata --python 3.11
```

#### **4) Create a uv-managed virtual environment**
```bash
uv venv
source .venv/bin/activate
```

On Windows (PowerShell):
```powershell
uv venv
.venv\Scripts\Activate.ps1
```

#### **5) Install dependencies with uv**
Use the existing `requirements.txt` with uv:
```bash
uv pip install -r requirements.txt
```

Recommended (project-managed) flow:
```bash
uv add -r requirements.txt
uv lock
uv sync
```

#### **6) Create database schema (recommended)**
The loader writes tables to schema `scrapper` in PostgreSQL. Create it once:
```sql
CREATE SCHEMA IF NOT EXISTS scrapper;
```

### **Environment Variables (.env)**
Create a `.env` file in the project root.

> **Important:** Never hardcode credentials in code, and never commit secrets to Git.

Example `.env`:
```env
# PostgreSQL connection string used by validate.py
POSTGRES_DSN=postgresql://username:password@localhost:5432/your_database

# Optional Mongo values (loaded but not used by the current PostgreSQL loader path)
MONGO_URI=
MONGO_DB=Scrapper_data

# Optional runtime settings
REPORTS_DIR=reports
HTTP_TIMEOUT=180
```

#### **Security best practices for `.env`**
- Add `.env` to `.gitignore`.
- Use separate credentials per environment (dev/staging/prod).
- Rotate credentials regularly.
- Use least-privilege DB users.

### **How the Project Works**
High-level workflow:

1. `main.py` selects a sector runner (or all runners).
2. Sector extractor fetches raw data from APIs/files.
3. Extractor shapes raw data into a tabular format with metadata fields.
4. `clean_transform.build_records(...)` standardizes rows into canonical record documents.
5. `validate.validate_and_load(...)`:
   - validates required fields,
   - normalizes country names,
   - drops invalid records,
   - writes a validation report,
   - upserts accepted records into PostgreSQL.

#### **Standardized record shape**
Each record includes:
- identity fields (`id`, `country`, `serial`)
- hierarchy (`sector`, `sub_sector`, `sub_sub_sector`, `metric`, `unit`)
- yearly values (`data_points` keyed by year)
- metadata (`source_link`, `sources`, timestamps, etc.)

This consistent shape is what makes cross-sector analytics possible.

### **Usage Instructions**

#### **Run one sector**
```bash
uv run python main.py run-sector --sector energy
```

Available sector keys:
- `energy`
- `aquastat`
- `nature`
- `adaptation`
- `cfcm`
- `mining`
- `infrastructure`

#### **Run all sectors**
```bash
uv run python main.py run-all --workers 4
```
- `--workers` controls parallelism.
- If omitted, project defaults to up to 4 workers.

#### **Expected output after runs**
- Terminal logs per sector.
- Validation report files in `reports/`.
- Upserted data in PostgreSQL tables under `scrapper.<collection_name>`.

### **Beginner-Friendly Guidance**
- **Extractor** = a script that pulls data from a source.
- **Transform** = cleaning and reshaping data into a consistent structure.
- **Validation** = checks that data is usable (required fields, country names).
- **Upsert** = insert new rows or update existing rows if IDs already exist.

If you are new to data engineering, think of this project as an assembly line:
- Source APIs are raw material,
- transform logic is the factory process,
- database tables are the finished products.

### **Best Practices (Data Engineering + Data Science)**

1. **Keep extraction separate from transformation**  
   This repo already follows that pattern through extractor modules + `build_records`.

2. **Use canonical dimensions**  
   The country normalization logic in `constants.py` prevents duplicate country variants.

3. **Treat schemas as contracts**  
   Avoid changing output field names casually; downstream dashboards depend on them.

4. **Track data quality continuously**  
   Always review generated validation reports before trusting downstream analysis.

5. **Use idempotent loads**  
   Upserts in `validate.py` allow re-runs without creating duplicate rows.

6. **Version and document data sources**  
   Keep source URLs and source names in records for traceability.

7. **Make failures observable**  
   Improve logging and alerting over time so API outages are visible quickly.

8. **Plan for reproducibility**  
   Pin dependencies, keep environment variables explicit, and run from a clean virtual environment.

### **Troubleshooting**
- **No rows loaded?** Check validation report in `reports/` for dropped-record reasons.
- **DB connection errors?** Verify `POSTGRES_DSN` and network access to PostgreSQL.
- **Missing countries in output?** Confirm country normalization mappings in `constants.py`.
- **API errors/timeouts?** Re-run and inspect extractor logs; many sources are external and may rate-limit.
